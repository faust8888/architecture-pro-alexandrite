# Архитектурное решение по логированию

Технический документ: внедрение централизованного сбора и анализа логов в системе «Александрит».

---

## 1. Анализ системы и C4-диаграммы в контексте логирования

### 1.1. Компоненты, из которых требуется сбор логов

По C4-диаграмме и описанию системы логи нужно собирать из:

| Компонент | Роль в потоке | Почему нужны логи |
|-----------|----------------|-------------------|
| **Shop API** | Приём заказа, сохранение в БД, загрузка 3D-файла в S3, публикация в RabbitMQ | Начало цепочки B2C; ошибки записи, публикации, загрузки — без логов разбор только со слов клиента. |
| **CRM API** | Обработка событий из RabbitMQ, создание/обновление заказов в Shop DB, работа продавцов | Критичное звено B2B; ошибки обработки сообщений = заказ не появляется в CRM — нужна причина в логах. |
| **MES API** | Расчёт стоимости, назначение на операторов, смена статусов, публикация событий | Узкое место по времени; ошибки расчёта, записи в MES db — без логов сложно локализовать. |
| **Internet Shop, CRM, MES (фронтенды)** | UI для клиентов, продавцов, операторов | Ошибки JS, сбои загрузки; при необходимости — логи клиентских ошибок. |
| **RabbitMQ** | Очередь сообщений между CRM и MES | Ошибки подключения, переполнение очередей, сообщения в DLQ — без логов поддержка не видит причину. |
| **Shop DB, MES db** | PostgreSQL (Managed) | Ошибки подключения, медленные запросы, блокировки; при наличии — аудит-логи. |

Фронтенды — SPA; приоритет — бэкенды (Shop API, CRM API, MES API) и RabbitMQ. Логи фронтенда можно добавить позже (Sentry, логи в бэкенд).

### 1.2. Список необходимых логов (уровень INFO)

| № | Событие | Система | Что логировать |
|---|---------|---------|----------------|
| 1 | Создание заказа | Shop API | Время (timestamp), order_id, customer_id (маскированный или хэш), source (b2c / b2b), статус (SUBMITTED) |
| 2 | Загрузка 3D-файла | Shop API | Время, order_id, file_id, размер (bytes), статус (успех/ошибка), причина ошибки при ошибке |
| 3 | Публикация сообщения в очередь | Shop API, CRM API, MES API | Время, order_id, message_type (order.submitted, order.price_calculated и т.д.), queue, статус |
| 4 | Получение и обработка сообщения из очереди | CRM API | Время, correlation_id/order_id, message_type, статус обработки (успех/ошибка), причина ошибки при ошибке |
| 5 | Изменение статуса заказа | Shop API, CRM API, MES API | Время, order_id, previous_status, new_status, actor (user_id или system) |
| 6 | Расчёт стоимости заказа | MES API | Время, order_id, длительность (ms), статус (успех/ошибка), причина ошибки при ошибке |
| 7 | Назначение заказа на оператора | MES API | Время, order_id, operator_id |
| 8 | Входной HTTP-запрос | Shop API, CRM API, MES API | Время, method, path, status_code, duration_ms, request_id (для связи с трейсом) |
| 9 | Ошибка внешнего вызова | Shop API, CRM API, MES API | Время, target (URL/сервис), order_id (если применимо), error_message, stack_trace (опционально) |
| 10 | Ошибка подключения к RabbitMQ | CRM API, MES API | Время, queue, error_message |
| 11 | Сообщение в DLQ | RabbitMQ / консьюмер | Время, queue, message_id, reason |

### 1.3. Другие уровни логирования

| Уровень | Когда использовать |
|---------|--------------------|
| **DEBUG** | Детали для отладки (тело запроса/ответа, промежуточные шаги). В prod — отключить или включать по флагу для конкретного order_id. |
| **INFO** | Обычные бизнес-события (создание заказа, смена статуса, публикация/обработка сообщений). |
| **WARN** | Неожиданные, но обрабатываемые ситуации: повторная попытка, fallback, деградация (например, таймаут при расчёте цены, fallback на кэш). |
| **ERROR** | Ошибки, требующие внимания: 5xx, исключения при обработке заказа, ошибки записи в БД, публикации в очередь. |
| **CRITICAL** | Критичные сбои: падение сервиса, недоступность БД или очереди, потеря данных. |

Рекомендация: в prod по умолчанию INFO и выше; DEBUG — только при целенаправленной отладке (по order_id или request_id).

## 2. Мотивация

### 2.1. Зачем добавлять логирование

- **Снижение времени разбора инцидентов.** Сейчас разбор идёт «со слов клиента» — разработчикам и поддержке нужно много времени, чтобы восстановить, что произошло. Централизованные логи по order_id, correlation_id, времени позволяют быстро увидеть цепочку событий и место сбоя.
- **Уменьшение нагрузки на поддержку.** Поддержка может самостоятельно искать в логах по order_id и отвечать клиенту, не эскалируя в разработку при каждой жалобе.
- **Основа для анализа и улучшений.** Логи дают данные: сколько заказов создаётся в час, как часто ошибки при расчёте цены, где узкие места по времени. Это основа для приоритизации доработок.
- **Аудит и соответствие.** Логирование изменений статусов и действий пользователей даёт аудит-след для расследования спорных ситуаций.

### 2.2. Что это даст компании

| Результат | Описание |
|-----------|----------|
| Сокращение MTTR | Быстрый поиск причины сбоя по order_id, correlation_id. |
| Меньше эскалаций в разработку | Поддержка может искать в логах сама. |
| Данные для оптимизации | Паттерны ошибок, пики нагрузки, медленные операции. |
| Аудит | Кто и когда изменил статус заказа. |

### 2.3. Технические и бизнес-метрики, на которые повлияет логирование

| Метрика | Как логирование влияет |
|---------|------------------------|
| **MTTR (Mean Time To Recovery)** | Сокращение за счёт быстрого поиска причины по логам. |
| **Время ответа поддержки клиенту** | Поддержка может смотреть логи по order_id и давать ответ без ожидания разработки. |
| **Количество эскалаций в разработку** | Часть обращений закрывается поиском по логам. |
| **Видимость «потерянных» заказов B2B** | По correlation_id видно, было ли сообщение обработано и с какой ошибкой. |
| **Качество SLA** | Можно строить отчёты по ошибкам, задержкам, объёму запросов. |

### 2.4. В каком порядке настраивать логирование и трейсинг

Команда не может одновременно включить логирование и трейсинг во всех системах. Рекомендуемый порядок:

| Приоритет | Системы | Обоснование |
|-----------|---------|-------------|
| 1 | **MES API, CRM API** | MES — узкое место (расчёт 2–30 мин), основная боль «заказ не появился» для B2B. CRM — точка приёма заказов из очереди; сбой здесь = заказ не виден партнёрам. |
| 2 | **Shop API** | Начало цепочки B2C; ошибки при создании заказа, загрузке 3D-файла, публикации в очередь. |
| 3 | **RabbitMQ** | Интеграция CRM–MES; логи очередей, DLQ помогают при «потерянных» заказах. |
| 4 | **Фронтенды (Internet Shop, CRM, MES)** | Ошибки UI; можно отложить или ограничиться сервисом ошибок (Sentry). |

Логирование и трейсинг лучше внедрять параллельно в одной и той же системе: логи дают контекст (order_id, текст ошибки), трейсинг — цепочку вызовов. Сначала MES API и CRM API, затем Shop API и RabbitMQ.

## 3. Предлагаемое решение

### 3.1. Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| **Сбор логов** | Filebeat / Fluent Bit | Лёгкий агент на инстансах; чтение логов из stdout/файлов, отправка в бэкенд. |
| **Транспорт** | HTTP / Kafka (опционально) | Filebeat отправляет в Elasticsearch/OpenSearch. При высокой нагрузке — через Kafka. |
| **Хранение и поиск** | OpenSearch / Elasticsearch | Полнотекстовый поиск, фильтрация по полям (order_id, service, level), индексы по сервисам. |
| **Визуализация** | OpenSearch Dashboards / Kibana | Дашборды, сохранённые поиски, опционально — алерты. |
| **Формат логов** | JSON (structured logging) | Единый формат с полями: timestamp, level, service, order_id, message, и т.д. |

### 3.2. Архитектура

- **На каждом инстансе (Shop API, CRM API, MES API):** приложение пишет JSON-логи в stdout; Filebeat/Fluent Bit читает и отправляет в OpenSearch.
- **RabbitMQ:** при наличии — экспортёр логов или логи management API; иначе — логи консьюмеров (CRM API, MES API) при обработке сообщений.
- **OpenSearch:** индексы по сервисам (shop-api, crm-api, mes-api), единый индекс для кросс-сервисного поиска по order_id.

Схема: на C4-диаграмме добавляются компоненты **Log Collector** (Filebeat на инстансах) и **Log Backend** (OpenSearch). Связи: Shop API, CRM API, MES API → Log Backend (через Filebeat).

**Диаграмма с компонентами логирования:** [resource/jewerly_c4_logging.drawio](../resource/jewerly_c4_logging.drawio)

### 3.3. Доработки приложений

| Компонент | Действия |
|-----------|----------|
| Shop API, CRM API | Structured logging (JSON): Logback/Log4j2 с JSON-encoder; добавление полей order_id, request_id, correlation_id в MDC; единый формат полей. |
| MES API | Аналогично: NLog/Serilog с JSON; order_id, request_id, correlation_id. |
| Все API | request_id в HTTP-заголовках и в логах для связи с трейсингом. |

### 3.4. Политика безопасности в отношении логов

| Аспект | Решение |
|--------|---------|
| **Чувствительные данные** | Не логировать: пароли, токены, полные номера карт. customer_id — маскировать (хэш или последние 4 цифры) или не логировать в prod. email/телефон — не логировать в свободном виде или маскировать. |
| **Доступ к логам** | Только сотрудники с ролью «Поддержка», «Разработчик», «DevOps», «Администратор». Аутентификация через корпоративный IdP (SSO). Аудит доступа к логам (кто, когда, что искал). |
| **Сеть** | Log Backend доступен только из внутренней сети/VPC. Трафик логов не выходит в интернет. |
| **Шифрование** | Логи в OpenSearch — шифрование at rest; передача по TLS. |

### 3.5. Политика хранения логов

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| **Индексы** | Отдельный индекс на сервис: `logs-shop-api-YYYY.MM.DD`, `logs-crm-api-YYYY.MM.DD`, `logs-mes-api-YYYY.MM.DD` | Фильтрация по сервису, управление retention по сервису. |
| **Срок хранения** | 30 дней (hot), опционально 90 дней (warm) для ERROR и выше | Баланс между объёмом и потребностью разбора инцидентов. |
| **Размер** | Оценка: ~1–5 GB/день при ~500–1000 заказов/день и типичном объёме логов | Планирование ресурсов OpenSearch; при росте — сжатие, cold tier. |
| **ILM (Index Lifecycle Management)** | Hot 7 дней, warm 23 дня, delete через 30 дней (или 90 для error) | Автоматическое удаление старых данных. |

## 4. Мероприятия для превращения сбора логов в анализ логов

### 4.1. Алертинг

| Алерт | Условие | Действие |
|-------|---------|----------|
| Рост ERROR | Более N ошибок в минуту по сервису (например, Shop API) | Уведомление в чат команды; при превышении порога — тикет. |
| Ошибки при обработке сообщений из очереди | Логи CRM API с «error» и «message_type» / «queue» | Уведомление — риск «потерянных» заказов B2B. |
| Ошибки расчёта стоимости | Логи MES API с «price calculate» и «error» | Уведомление — заказы застревают в ожидании цены. |
| Сообщения в DLQ | Событие «message in DLQ» (из мониторинга RabbitMQ или логов) | Уведомление + тикет на разбор. |

### 4.2. Поиск аномалий

| Аномалия | Как детектировать | Действие |
|----------|-------------------|----------|
| Резкий рост создания заказов | Количество логов «order.created» за единицу времени (например, за минуту) — рост в 10–100 раз | Возможный DDoS или аномальная нагрузка; алерт, проверка источника. |
| Резкий рост ошибок | Количество ERROR по сервису — рост относительно базового уровня | Алерт, разбор причин. |
| Падение числа успешных расчётов цены | Доля успешных «price.calculate» — падение | Возможная деградация MES; алерт. |
| Задержка обработки сообщений | Время между «message published» и «message processed» — рост | Очередь перегружена или консьюмер тормозит; алерт. |

Реализация: запросы в OpenSearch Dashboards (Saved Searches + Alerts) или отдельный сервис, который периодически агрегирует метрики из логов и сравнивает с порогами. При росте — интеграция с Prometheus/Alertmanager для единого канала уведомлений.

## 5. Критерии выбора технологии для работы с логами

### 5.1. Сравнительная таблица

| Критерий | ELK (Elasticsearch + Kibana) | OpenSearch + Dashboards | Splunk | Loki + Grafana |
|----------|------------------------------|--------------------------|--------|----------------|
| **Лицензия** | Elastic License (ограничения на SaaS) | Apache 2.0 | Проприетарная | Apache 2.0 (Loki), AGPL (Grafana) |
| **Стоимость** | Бесплатно self-hosted; платно при облачном Elasticsearch | Бесплатно, open source | Высокая (enterprise) | Бесплатно |
| **Масштабируемость** | Хорошая, горизонтальное масштабирование | Аналогично ES | Очень хорошая | Хорошая для логов, индексация по меткам |
| **Поиск по полям** | Полнотекстовый + structured | Аналогично | Очень мощный | Индексирует метки; полнотекст ограничен |
| **Интеграция с Yandex Cloud** | Managed Elasticsearch (есть) | Managed OpenSearch (есть) | Через партнёров | Self-hosted или Grafana Cloud |
| **Кривая обучения** | Средняя | Средняя (форк ES) | Высокая | Ниже для команд, знакомых с Grafana |
| **Поддержка JSON/structured logs** | Отличная | Отличная | Отличная | Хорошая (метки + content) |

### 5.2. Рекомендация

**OpenSearch** — оптимальный вариант для «Александрита»:

| Плюсы | Минусы |
|-------|--------|
| Apache 2.0 — нет лицензионных ограничений при использовании в облаке | Форк Elasticsearch — возможны отличия от актуального ES |
| Совместим с экосистемой Elasticsearch (Filebeat, индексы) | Нужны ресурсы на развёртывание и поддержку |
| Managed OpenSearch в Yandex Cloud (если доступен) | |
| Полнотекстовый поиск, фильтрация по полям, дашборды | |
| Хорошая документация и сообщество | |

**Альтернатива:** ELK, если команда уже использует Elasticsearch и готова учитывать лицензию. Loki — если приоритет интеграция с Grafana и хранение только меток + ссылки на объектное хранилище.

## 6. Схема: компоненты логирования

На диаграмме C4 добавляются:

- **Log Backend** (OpenSearch) — приём, хранение и поиск логов (выделен оранжевым).
- **Log Collector** (Filebeat) — на инстансах Shop API, CRM API, MES API; собирает логи из stdout и отправляет в Log Backend.

Связи: Shop API, CRM API, MES API → Log Backend (логи передаются через Filebeat).

**Диаграмма:** [resource/jewerly_c4_logging.drawio](../resource/jewerly_c4_logging.drawio)
