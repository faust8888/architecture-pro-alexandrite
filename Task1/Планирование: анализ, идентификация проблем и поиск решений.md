# Планирование: анализ, идентификация проблем и поиск решений

## 1. Идентификация проблемных мест

### 1.1. Бизнес-критичные (влияют на выручку и репутацию)

| № | Проблема | Источник |
|---|----------|----------|
| P1 | **Клиенты не получают заказы вовремя** — жалобы на просрочки (обещали 3 недели, работают месяцами). Растёт недовольство B2C-клиентов. | task.md |
| P2 | **Партнёры по API не получают заказы** — представители компаний ежедневно сообщают об отсутствии заказов. Потеря нескольких крупных контрактов через месяц после открытия API. | task.md |
| P3 | **Нет прозрачности статуса заказа** — клиент и партнёр не видят, на каком этапе заказ, кто отвечает, когда ожидать. Это усиливает ощущение «заказа нет». | Анализ потока данных |
| P4 | **Рост нагрузки не обеспечен архитектурно** — +100 заказов/месяц, плюс B2B через API. Один инстанс на приложение, одна БД на запись и чтение. Риск перегрузки и простоев. | task.md, описание инфраструктуры |

### 1.2. Производительность и масштабируемость

| № | Проблема | Источник |
|---|----------|----------|
| P5 | **Медленная первая страница MES (дашборд)** — долгая загрузка списка заказов в работе. Фильтр по статусам и пагинация не помогли. Операторам критично видеть самые новые заказы (влияет на вознаграждение). | task.md |
| P6 | **Долгий расчёт стоимости** — 2–3 минуты в среднем, до 30 минут для сложных моделей. Расчёт только в MES, блокирует дальнейший поток заказа. | task.md |
| P7 | **Единая БД Shop DB на запись и чтение** — Shop API и CRM API используют одну БД без разделения read/write. При росте нагрузки станет узким местом. | Схема C4, описание инфраструктуры |

### 1.3. Согласованность данных и интеграции

| № | Проблема | Источник |
|---|----------|----------|
| P8 | **Два источника правды по заказам** — заказы и статусы живут в Shop DB (онлайн-магазин/CRM) и в MES db. Синхронизация через RabbitMQ. Возможны рассинхрон, «потерянные» заказы в отчётах и в API. | Схема C4, сценарий B2B |
| P9 | **Сценарий B2B завязан на очередь** — заказ создаётся в CRM по сообщению от MES. При сбоях очереди или задержках сообщений партнёры не видят заказы в CRM. | task.md |
| P10 | **Нет единого идентификатора/трекинга заказа** — при жалобе «не получил заказ» сложно однозначно сопоставить заказ в магазине, CRM и MES. | Анализ потока |

### 1.4. Процессы и качество

| № | Проблема | Источник |
|---|----------|----------|
| P11 | **Релизы блокируются багами high/highest** — ручное E2E на тестовом окружении, при обнаружении серьёзных багов продакшн не деплоят. Задержки релизов растут (раньше до месяца, сейчас больше). | task.md |
| P12 | **Ручной деплой в release и prod** — увеличивает время выката и риск человеческой ошибки. | task.md |
| P13 | **Один инстанс на окружение** — нет отказоустойчивости; при падении приложения или БД сервис недоступен. | Описание инфраструктуры |

### 1.5. Потенциальные риски

| № | Проблема | Источник |
|---|----------|----------|
| P14 | **RabbitMQ как единая шина** — при проблемах с очередью нарушается обмен между CRM и MES (в т.ч. создание заказов из API). Нет описанной стратегии retry/DLQ и мониторинга. | Схема, описание |
| P15 | **Нет явного лимитирования и приоритизации API** — после открытия API «завалило заказами». Риск перегрузки MES и очередей, ухудшение SLA для всех каналов. | task.md |

## 2. Список инициатив для устранения проблем

| № | Инициатива | Решаемые проблемы | Тип |
|---|------------|-------------------|-----|
| I1 | **Единый трекинг статуса заказа (Order Tracking)** — единый источник статуса для клиента и партнёра (портал/виджет/API), данные из CRM или агрегация из CRM + MES с задержкой не более допустимой. | P1, P2, P3, P10 | Функциональность + доверие |
| I2 | **Оптимизация дашборда MES** — переработка первой страницы: кэш/материализованные представления, индексы, отдельный read-слой или CQRS для списка заказов; приоритет «новые первые», быстрая загрузка без тяжёлых запросов. | P5 | Производительность |
| I3 | **Асинхронный расчёт стоимости** — не блокировать создание заказа: заказ создаётся сразу, расчёт стоимости выполняется в фоне (очередь задач), клиент/партнёр получает уведомление или проверяет статус (связка с I1). | P6, частично P1, P2 | Архитектура + UX |
| I4 | **Разделение чтения и записи для Shop DB (read replica)** — вынести тяжёлые чтения (списки заказов, отчёты, дашборды) на реплику; запись оставить на primary. | P7, P5 (если часть дашбордов в CRM) | Инфраструктура |
| I5 | **Надёжность очередей и интеграции CRM–MES** — явные retry, DLQ, мониторинг очередей; идемпотентность обработки сообщений; опционально — саги/компенсации для сценария «заказ из API». | P8, P9, P14 | Надёжность |
| I6 | **Единый идентификатор заказа и контракт обмена** — сквозной order_id, единый формат сообщений между Shop/CRM и MES; документированный контракт (например, OpenAPI/события). | P8, P10, P9 | Архитектура данных |
| I7 | **Лимиты и приоритизация для B2B API** — rate limiting, квоты, приоритеты очередей (например, B2C vs B2B) или отдельные воркеры, чтобы один канал не «забивал» другой. | P15, P4 | Управление нагрузкой |
| I8 | **Масштабирование и отказоустойчивость** — минимум два инстанса для критичных приложений (MES API, CRM API, Shop API); балансировщик; по возможности — несколько инстансов БД (primary + replica). | P4, P13 | Инфраструктура |
| I9 | **Автоматизация тестирования и деплоя** — автоматические E2E/интеграционные тесты в CI; автоматический деплой в release (и по возможности в prod по approval). Снижение зависимости от ручного прогона. | P11, P12 | Процессы |
| I10 | **Мониторинг и алертинг** — метрики по заказам (создано/просрочено/застряло в статусе), время расчёта стоимости, длина очередей, ошибки интеграций. Быстрая реакция на сбои. | P1, P2, P14, P5 | Observability |
| I11 | **Отдельный read-слой или кэш для списков заказов в MES** — если I2 недостаточно: отдельная БД/слой для чтения (CQRS) или кэш (Redis) с инвалидацией по событиям из MES. | P5 | Архитектура |

## 3. Приоритизация инициатив

### 3.1. Критерии приоритизации

- **Влияние на жалобы клиентов и партнёров** (P1, P2, P3) — максимальный приоритет.
- **Влияние на операционную работу** (дашборд MES, P5) — прямо влияет на вознаграждение операторов и скорость обработки.
- **Снижение риска потери заказов и контрактов** (очереди, консистентность, трекинг).
- **Возможность реализовать силами текущей команды** (без массового найма).
- **Зависимости** — часть инициатив упрощает другие (например, I6 помогает I1 и I5).

### 3.2. Порядок приоритетов (от высшего к низшему)

| Приоритет | Инициатива | Обоснование |
|-----------|------------|-------------|
| 1 | **I1 — Единый трекинг статуса заказа** | Закрывает главный запрос «где мой заказ» для B2C и B2B, снижает поток беспокойств и потери контрактов. Даёт измеримый результат для бизнеса. |
| 2 | **I2 — Оптимизация дашборда MES** | Критично для операторов (вознаграждение) и для скорости обработки заказов. Быстро снимает боль без переписывания всей системы. |
| 3 | **I5 — Надёжность очередей CRM–MES** | Устраняет «потерянные» заказы из API и сбои синхронизации. Основа для стабильной работы B2B и консистентности. |
| 4 | **I3 — Асинхронный расчёт стоимости** | Убирает длительное ожидание при оформлении, улучшает UX и разгружает поток. Требует согласования с I1 (уведомление о готовности цены). |
| 5 | **I6 — Единый идентификатор и контракт обмена** | Фундамент для трекинга (I1), отладки и будущих интеграций. Логично делать параллельно или сразу после I1. |
| 6 | **I10 — Мониторинг и алертинг** | Позволяет видеть просрочки, застрявшие заказы и сбои очередей. Поддерживает все остальные инициативы. |
| 7 | **I7 — Лимиты и приоритизация B2B API** | Защита от перегрузки после открытия API. Важно при дальнейшем росте B2B. |
| 8 | **I4 — Read replica для Shop DB** | Снимает нагрузку с БД при росте; полезно после стабилизации очередей и дашборда. |
| 9 | **I9 — Автоматизация тестирования и деплоя** | Снижает задержки релизов и риски. Долгосрочная инвестиция в процесс. |
| 10 | **I8 — Масштабирование (несколько инстансов)** | Нужно при дальнейшем росте нагрузки; после оптимизаций и лимитов можно планировать по метрикам. |
| 11 | **I11 — Отдельный read-слой/кэш для MES** | Рассматривать, если I2 не даст нужного эффекта. |

## 4. Целевая архитектура через полгода

Через полгода целесообразно видеть следующее состояние:

- **Прозрачность заказа**
  - Единый трекинг статуса заказа (I1) для клиента и партнёра (сайт, личный кабинет, API).
  - Сквозной идентификатор заказа и согласованный контракт обмена (I6) между Shop/CRM и MES.

- **Стабильность и предсказуемость**
  - Надёжная работа очередей CRM–MES (I5): retry, DLQ, мониторинг, идемпотентность.
  - Асинхронный расчёт стоимости (I3): заказ создаётся сразу, цена приходит позже с уведомлением/обновлением статуса.

- **Производительность критичных экранов**
  - Быстро загружающийся дашборд MES (I2) за счёт оптимизации запросов и, при необходимости, кэша/read-слоя.

- **Управление нагрузкой и наблюдаемость**
  - Лимиты и приоритизация для B2B API (I7).
  - Базовый мониторинг заказов и интеграций (I10): просрочки, застрявшие статусы, очереди, ошибки.

- **Инфраструктура и процессы**
  - По возможности — read replica для Shop DB (I4) для разгрузки отчётов и списков.
  - Первые шаги к автоматизации тестов и деплоя (I9); решение о нескольких инстансах (I8) — по результатам метрик и нагрузки.

Итог: не «революция» архитектуры, а **целенаправленное снятие критичных болей** (трекинг, дашборд MES, очереди, расчёт стоимости) и закладка основы для масштабирования (контракты, мониторинг, лимиты).

## 5. Три инициативы на ближайшие полгода (если можно выбрать только три)

Если ограничиться **тремя** инициативами на полгода, разумный выбор:

### 1. **I1 — Единый трекинг статуса заказа (Order Tracking)**

- **Почему:** Главная боль — «клиент/партнёр не получил заказ» и «не видно, где заказ». Трекинг напрямую снижает недоверие и количество обращений, помогает удерживать контракты.
- **Что даёт:** Один понятный источник статуса для B2C и B2B, меньше звонков менеджерам и меньше эскалаций.

### 2. **I2 — Оптимизация дашборда MES (первая страница)**

- **Почему:** Медленная загрузка списка заказов бьёт по операторам (вознаграждение за «новые» заказы) и по скорости обработки. Реализуемо в рамках текущего стека (индексы, запросы, при необходимости кэш/материализованные представления).
- **Что даёт:** Быстрый отклик первой страницы MES, меньше жалоб операторов, выше эффективность производства.

### 3. **I5 — Надёжность очередей и интеграции CRM–MES**

- **Почему:** Заказы из B2B API создаются в CRM по сообщениям из MES. Сбои очереди или потери сообщений приводят к «не получили заказ» и к потере контрактов. Без стабильной шины остальные улучшения менее эффективны.
- **Что даёт:** Меньше потерянных и «зависших» заказов, предсказуемая доставка событий, основа для последующих изменений (I3, I6).

**Почему не вошли в топ-3 (при ограничении):**

- **I3 (асинхронный расчёт)** — сильно улучшает UX, но требует согласованной работы с трекингом (I1) и очередями (I5). Логичный следующий шаг после этой тройки.
- **I6 (единый ID и контракт)** — важен для долгосрочной согласованности и для I1, но первый эффект для пользователя даёт именно I1; I6 можно вести параллельно в меньшем объёме (например, только формат и идентификатор).
- **I10 (мониторинг)** — желательно внедрять по мере реализации I1, I2, I5 (минимальный набор метрик и алертов), но как отдельная «большая» инициатива уступает по срочности трём выбранным.

Итого: **трекинг заказа** + **быстрый дашборд MES** + **надёжные очереди** дают максимальный эффект для клиентов, партнёров и операторов при ограничении в три инициативы на полгода.
