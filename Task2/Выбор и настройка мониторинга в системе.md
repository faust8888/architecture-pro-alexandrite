# Выбор и настройка мониторинга в системе «Александрит»

Технический документ: мониторинг приложений, баз данных, очередей и хранилища в контексте системы ювелирного производства и онлайн-продаж.

---

## 1. Анализ системы и C4-диаграммы в контексте мониторинга

### 1.1. Компоненты системы (по C4)

| Компонент | Технология | Роль в мониторинге |
|-----------|------------|---------------------|
| **Internet Shop** (фронт) + **Shop API** (бэкенд) | Vue, Spring Boot | Точка входа B2C; объём и качество запросов, латентность, ошибки. |
| **CRM** (фронт) + **CRM API** (бэкенд) | Vue, Spring Boot | Работа продавцов; приём заказов из очереди от MES (B2B). Критична доступность и консистентность с очередью. |
| **MES** (фронт) + **MES API** (бэкенд) | React, C# | Расчёт стоимости, назначение заказов операторам, дашборд. Узкое место по производительности и нагрузке от B2B API. |
| **Messages Queue** (RabbitMQ) | RabbitMQ | Связь CRM ↔ MES: новые заказы, смена статусов. Сбои ведут к «потерянным» заказам и жалобам партнёров. |
| **Shop DB** | PostgreSQL (Managed, Yandex Cloud) | Общие данные для Shop API и CRM API. Один инстанс на запись и чтение — риск перегрузки. |
| **MES db** | PostgreSQL (Managed) | Заказы и статусы с точки зрения MES. Нагрузка от дашборда и расчётов. |
| **3d files storage** | S3-совместимое хранилище | Хранение 3D-моделей для расчёта стоимости. Рост объёма и доступность влияют на расчёты. |

### 1.2. Критичные потоки для наблюдения

- **B2C:** Клиент → Shop → Shop API → Shop DB; заказ уходит в очередь → CRM → MES (расчёт цены, производство).
- **B2B:** API-пользователь → MES API (расчёт) → очередь → CRM (создание заказа в CRM). Сбой очереди = заказ не появляется в CRM.
- **Операторы:** MES (дашборд) → MES API → MES db. Медленный ответ = жалобы и просадка эффективности.

Яндекс Метрика покрывает только поведение пользователей на сайте и не видит: API B2B, внутренние сервисы, очереди, БД, латентность бэкендов. Для улучшения системы и обоснования решений нужен технический и бизнес-мониторинг.

## 2. Мотивация

### 2.1. Зачем добавлять мониторинг

- **Снижение потери контрактов и репутации.** Жалобы «не получили заказ» и просрочки уже привели к потере крупных B2B-контрактов. Без метрик нельзя понять: задержка в очереди, падение API, перегрузка MES или БД. Мониторинг даёт возможность реагировать до эскалации в бизнес.
- **Объективная картина нагрузки.** Рост +100 заказов/месяц и «завалило заказами» после открытия API — качественные формулировки. RPS по каналам (B2C / B2B), латентность, использование CPU/RAM и БД покажут, где узкое место и когда планировать масштабирование.
- **Быстрая диагностика сбоев.** Долгая загрузка дашборда MES, ошибки 500, сообщения в DLQ — без метрик и алертов команда узнаёт о проблеме от пользователей. С мониторингом — по алерту и графикам, с привязкой к компоненту (API, БД, очередь).
- **Обоснование затрат для бизнеса.** Решения «добавить инстанс», «настроить очереди», «оптимизировать дашборд» требуют ресурсов. Графики «время ответа MES API», «очередь сообщений», «просроченные заказы» переводят технические риски в понятные бизнес-последствия и помогают приоритизировать задачи.

### 2.2. Что это даёт компании

| Результат | Описание |
|-----------|----------|
| Раннее обнаружение проблем | Алерты по ошибкам, латентности, очередям и насыщенности ресурсов до массовых жалоб. |
| Данные для приоритизации | Видно, какой сервис/канал перегружен; проще обосновать, что делать в первую очередь (дашборд MES, очереди, API). |
| Связь техники и бизнеса | Метрики по заказам (созданные, застрявшие, просроченные) дополняют Яндекс Метрику и дают полную картину воронки. |
| Основа для SLA и лимитов | RPS и латентность по API позволяют обсуждать с партнёрами реалистичные SLA и вводить rate limiting обоснованно. |

## 3. Выбор подхода к мониторингу

Для разных частей системы используются разные подходы.

### 3.1. Request-ориентированные сервисы (API): RED

**Rate, Errors, Duration** — для Shop API, CRM API, MES API.

- **Rate** — число запросов в единицу времени (RPS). Нужен по каждому API и, где возможно, по типу (например, B2C vs B2B для MES).
- **Errors** — доля или количество неуспешных ответов (5xx, при необходимости 4xx по кодам). Позволяет видеть деградацию качества сервиса.
- **Duration** — латентность (например, p50, p95, p99). Критично для MES (дашборд и расчёт стоимости) и для UX магазина.

Обоснование: эти сервисы обслуживают запросы пользователей и партнёров; RED напрямую отражает доступность и качество сервиса.

### 3.2. Ресурсы (инстансы приложений и БД): USE

**Utilization, Saturation, Errors** — для CPU и памяти API, для БД (память, соединения), при необходимости для диска.

- **Utilization** — загрузка ресурса (CPU %, память). Показывает, насколько ресурс занят.
- **Saturation** — «перегрузка» (очередь задач, ожидание). Для БД — число активных/ожидающих соединений; для приложений — очередь запросов или потоков.
- **Errors** — сбои использования ресурса (OOM, отказ соединения к БД и т.п.).

Обоснование: при одном инстансе на приложение и одной БД на запись/чтение перегрузка ресурса ведёт к деградации или падению. USE помогает планировать масштабирование и алерты по насыщенности.

### 3.3. Очереди (RabbitMQ): «Четыре золотых сигнала» + специфика очередей

- **Latency** — время от появления сообщения в очереди до его обработки (consumer lag). Важно для сценария «заказ из API не появился в CRM».
- **Traffic** — объём сообщений (входящих/исходящих, при необходимости по типам или очередям).
- **Errors** — сообщения в Dead Letter (DLQ), сбои подключения, отказы консьюмеров.
- **Saturation** — глубина очереди, число сообщений in flight. Рост указывает на отставание консьюмеров или перегрузку.

Обоснование: интеграция CRM–MES полностью завязана на RabbitMQ; потеря или задержка сообщений напрямую приводит к жалобам партнёров и «потерянным» заказам.

### 3.4. Сводка по компонентам

| Компонент | Подход | Основные акценты |
|-----------|--------|-------------------|
| Shop API, CRM API, MES API | RED | RPS, ошибки (5xx), латентность (p95, p99). |
| Инстансы Shop API, CRM API, MES API | USE | CPU %, Memory utilisation. |
| Shop DB, MES db | USE | Memory, число соединений; при наличии — I/O wait, размер БД. |
| RabbitMQ | Золотые сигналы + очереди | DLQ, сообщения in flight, глубина очередей, при необходимости consumer lag. |
| S3 (3d files storage) | Насыщенность / объём | Размер хранилища, при необходимости количество объектов. |

## 4. Метрики: что отслеживать и зачем

### 4.1. Метрики из предложенного списка

#### RabbitMQ

| Метрика | Зачем нужна | Ярлыки (labels) |
|---------|-------------|------------------|
| **Number of dead-letter-exchange letters** | Сообщения, которые не удалось обработать. Рост = сбои интеграции и риск «потерянных» заказов (в т.ч. B2B). | `queue`, `reason` (если доступно в RabbitMQ). |
| **Number of messages in flight** | Сообщения, взятые консьюмером, но ещё не подтверждённые. Рост может означать долгую обработку или «зависание» консьюмера. | `queue`, `consumer_tag` (опционально). |

#### RPS (запросы в секунду) по API

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Number of requests (RPS) for Internet Shop API** | Нагрузка от B2C; тренд роста и пики; планирование масштабирования. | `method`, `path` (или группа эндпоинтов), `status_class` (2xx/4xx/5xx). |
| **Number of requests (RPS) for CRM API** | Нагрузка от продавцов и внутренних вызовов; влияние на общую систему. | `method`, `path` (или группа), `status_class`. |
| **Number of requests (RPS) for MES API** | Суммарная нагрузка от операторов (MES UI) и B2B API. Критично для понимания, кто создаёт пики. | `method`, `path` (или группа), `status_class`, **`source`** (например: `ui` / `b2b_api`) — если удаётся разнести. |

RPS per user из списка (для каждого API) полезны для обнаружения аномалий по одному пользователю (злоупотребление, баг клиента). Ярлыки: `user_id` или `client_id` (анонимизированный), `api` (shop/crm/mes). Требует осторожности с объёмом кардинальности; можно ограничить топ-N пользователей по RPS или считать только при алерте по общему RPS.

#### Ресурсы приложений (USE)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **CPU % for Shop API, CRM API, MES API** | Утилизация процессора; приближение к насыщенности и необходимость масштабирования. | `host`, `instance` (если несколько инстансов). |
| **Memory utilisation for Shop API, CRM API, MES API** | Риск OOM и деградации; планирование лимитов и масштабирования. | `host`, `instance`. |
| **Memory utilisation for Shop DB, MES db** | Нагрузка на БД; связь с медленными запросами и числом соединений. | `instance` (имя инстанса БД). |
| **Number of connections for Shop DB, MES db** | Насыщенность: исчерпание пула соединений ведёт к ошибкам приложений. | `state` (active/idle), при возможности `application` (shop_api / crm_api). |

#### Латенция (RED)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Response time (latency) for Shop API, CRM API, MES API** | Качество сервиса; для MES напрямую связано с жалобами на «долго грузится». Рекомендуется хранить перцентили (p50, p95, p99). | `method`, `path` (или группа), `status_class`. |

#### Размеры хранилищ

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Size of S3 storage** | Рост объёма 3D-файлов; планирование квот и затрат; риск заполнения. | `bucket` (если несколько). |
| **Size of Shop DB, MES db** | Рост данных; планирование бэкапов и масштабирования. | `instance`. |

#### Ошибки (RED / золотые сигналы)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Number of HTTP 5xx for Shop API, CRM API, MES API** | Количество ошибок сервера; алертинг при росте. | `method`, `path` (или группа), `status_code`. |
| **Number of HTTP 2xx** (опционально) | Нормальная активность; можно выводить как RPS по 2xx или долю успешных. | Аналогично RPS. |

#### Сессии и трафик (дополнительный контекст)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Number of simultaneous sessions for Shop API, CRM API, MES API** | Оценка текущей нагрузки пользователями; связь с RPS и памятью. | `api`. |
| **Kb transferred (received/sent) for each API** | Объём трафика; полезно для сетевых лимитов и аномалий (например, утечка больших ответов). | `api`, `direction` (in/out). |

### 4.2. Дополнительные метрики (вне списка)

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| **Глубина очередей RabbitMQ** (по очередям) | Рост глубины = накопление необработанных сообщений, риск задержки создания заказов в CRM. | `queue`. |
| **Количество заказов в статусе «ожидание расчёта цены»** (например, SUBMITTED без PRICE_CALCULATED) старше N минут | Бизнес-индикатор «застрявших» заказов; связь с очередью и MES. | `source` (b2c / b2b). |
| **Количество заказов просроченных** (дедлайн доставки прошёл, статус не CLOSED) | Прямой индикатор для жалоб «не получил заказ»; приоритет для поддержки. | — |
| **Время расчёта стоимости заказа** (от постановки в очередь до PRICE_CALCULATED) | Отражает реальное время обработки MES; выявление задержек 2–30 мин. | `source` (b2c / b2b). |

Эти метрики требуют источника данных из приложений или БД (логирование событий заказа, выдача в Prometheus/аналог) и согласованных статусов из Task1.

## 5. План действий (драфт технического задания)

### 5.1. Инфраструктура сбора и хранения метрик

1. **Выбор и развёртывание системы метрик**
   - Ввести time-series хранилище метрик (например, Prometheus или облачный аналог в Yandex Cloud, совместимый с Prometheus).
   - Определить окружения: как минимум prod; при возможности — release и dev для отладки дашбордов и алертов.

2. **Сбор метрик с приложений**
   - Включить экспорт метрик в формате Prometheus в Shop API, CRM API, MES API (Spring Boot Actuator + Micrometer, для C# — аналог, например OpenTelemetry или встроенные счётчики с экспортом).
   - Собирать RPS, латентность (гистограммы), 5xx, сессии; при необходимости разнести MES API по `source` (ui / b2b_api) через middleware или конфигурацию.

3. **Сбор метрик с БД и очередей**
   - Подключить экспортёр метрик для PostgreSQL (например, postgres_exporter): память, соединения, размер БД.
   - Подключить экспортёр для RabbitMQ (например, rabbitmq_prometheus или встроенный plugin): очереди (глубина, in flight), DLQ, при необходимости consumer lag.
   - Сбор метрик с EC2 (CPU, память) — node_exporter или облачной интеграции Yandex Cloud.

4. **Сбор метрик по S3**
   - Использовать облачную метрику размера бакета (Yandex Object Storage) или периодический скрипт/задание, экспортирующее размер в ту же систему метрик.

5. **Бизнес-метрики по заказам**
   - Реализовать в одном из бэкендов (CRM API или отдельный небольшой сервис) подсчёт: заказы в статусе «ожидание расчёта» > N минут, просроченные заказы, при необходимости — время от SUBMITTED до PRICE_CALCULATED. Экспорт в ту же систему метрик (например, кастомные gauge/counter в Prometheus).

### 5.2. Визуализация и алертинг

6. **Дашборды**
   - Создать дашборды (Grafana или аналог в облаке): по одному на группу (API, БД, очереди, бизнес-метрики). Поверх дашбордов — RED по API, USE по ресурсам, очереди и заказы по описанным метрикам.

7. **Правила алертинга**
   - Описать и внедрить правила: рост 5xx, превышение порогов латентности (p95), рост DLQ и глубины очередей, превышение порогов по CPU/памяти/соединениям, рост «застрявших» и просроченных заказов (см. раздел 6). Каналы уведомлений: чат команды, при критичных — эскалация (тикет, ответственный).

### 5.3. Документация и процессы

8. **Документирование**
   - Зафиксировать список метрик, их смысл, ярлыки и расположение на дашбордах. Описать процедуру реагирования на алерты (кто смотрит, когда эскалировать, как закрывать инцидент).

9. **Ревью и итерация**
   - После первых недель работы — ревью алертов (ложные срабатывания, пропуски). Скорректировать пороги и состав метрик.

## 6. Показатели насыщенности и действия при их превышении

**Насыщенность** здесь понимается как достижение порогов, после которых качество сервиса падает или высок риск сбоя. Ниже — пороговые значения и действия.

### 6.1. Инстансы приложений

| Ресурс | Пороговое значение | Обоснование | Действие при превышении |
|--------|--------------------|------------|--------------------------|
| **CPU % (Shop API, CRM API, MES API)** | Предупреждение: 70%; Критично: 85% | Выше 70% — мало запаса при пиках; выше 85% — риск деградации и таймаутов. | **Warning:** уведомление в чат команды, задача на анализ нагрузки (кто нагружает, какой эндпоинт). **Critical:** уведомление + тикет с приоритетом; рассмотреть срочное масштабирование (добавить инстанс) или временное ограничение нагрузки (rate limit). |
| **Memory utilisation (Shop API, CRM API, MES API)** | Предупреждение: 75%; Критично: 90% | Близко к лимиту контейнера/машины — риск OOM. | **Warning:** алерт в чат, проверка утечек и профиля памяти. **Critical:** тикет + рассмотрение перезапуска/масштабирования до OOM. |

### 6.2. Базы данных

| Ресурс | Пороговое значение | Обоснование | Действие при превышении |
|--------|--------------------|------------|--------------------------|
| **Number of connections (Shop DB, MES db)** | Предупреждение: 80% от max_connections; Критично: 95% | Исчерпание соединений = ошибки приложений при новых запросах. | **Warning:** алерт в чат, проверка утечек соединений и пулов в приложениях. **Critical:** тикет, срочная проверка долгих запросов и блокировок; при необходимости увеличение max_connections или масштабирование (read replica, пересмотр пулов). |
| **Memory utilisation (Shop DB, MES db)** | Предупреждение: 80%; Критично: 95% | Высокая нагрузка на БД, риск swap и падения производительности. | **Warning:** уведомление, анализ тяжёлых запросов. **Critical:** тикет, координация с облачным провайдером (масштабирование инстанса БД) или оптимизация запросов. |

### 6.3. RabbitMQ

| Метрика | Пороговое значение | Обоснование | Действие при превышении |
|---------|--------------------|------------|--------------------------|
| **Number of messages in DLQ** | Предупреждение: > 0; Критично: рост на N за короткий интервал (например, +10 за 5 мин) | Любое сообщение в DLQ — сбой обработки; быстрый рост — массовая ошибка интеграции. | **Warning:** алерт в чат, разбор причины (логи консьюмера, формат сообщения). **Critical:** тикет, приостановка повторной обработки до выяснения; исправление консьюмера/формата; ручная обработка или реимпорт сообщений после починки. |
| **Number of messages in flight** (суммарно или по критичной очереди) | Предупреждение: стабильно выше обычного уровня (например, 2x от медианы за неделю); Критично: рост без снижения (подозрение на «зависание» консьюмера) | Рост in flight — сообщения не подтверждаются; риск дублирования или потери при падении консьюмера. | **Warning:** проверка консьюмеров (логи, нагрузка). **Critical:** тикет, проверка здоровья консьюмеров CRM/MES; перезапуск консьюмера при необходимости. |
| **Глубина очереди** (очередь заказов в CRM) | Предупреждение: > 100; Критично: > 500 или рост > 50/мин | Накопление = задержка появления заказов в CRM; партнёры не видят заказы. | **Warning:** алерт, оценка пропускной способности консьюмеров. **Critical:** тикет, масштабирование воркеров консьюмера или временное ограничение приёма заказов через API (rate limit), уведомление партнёров при необходимости. |

### 6.4. Хранилища

| Метрика | Пороговое значение | Обоснование | Действие при превышении |
|---------|--------------------|------------|--------------------------|
| **Size of S3 storage** | Предупреждение: 80% квоты; Критично: 95% | Заполнение = невозможность загрузки новых 3D-моделей, сбой заказов. | **Warning:** тикет на планирование расширения квоты или очистки старых файлов. **Critical:** срочный тикет, коммуникация с облачным провайдером (увеличение квоты), при необходимости временное ограничение загрузки и уведомление бизнеса. |
| **Size of Shop DB / MES db** | Предупреждение: 80% выделенного объёма; Критично: 90% | Рост до лимита — риск остановки записи и падения сервиса. | **Warning:** тикет на увеличение объёма или архивирование старых данных. **Critical:** срочное увеличение объёма (облако) или экстренная очистка/архивация; уведомление команды и бизнеса. |

### 6.5. Бизнес-насыщенность (заказы)

| Метрика | Пороговое значение | Обоснование | Действие при превышении |
|---------|--------------------|------------|--------------------------|
| **Заказы в статусе «ожидание расчёта цены» > 15 минут** | Предупреждение: > 20; Критично: > 50 | Обещание «быстрый расчёт» нарушается; клиенты и партнёры не видят цену. | **Warning:** алерт в чат, проверка очереди и MES (расчёт стоимости). **Critical:** тикет, проверка воркеров MES и очередей; при необходимости масштабирование воркеров расчёта; информирование поддержки для коммуникации с клиентами. |
| **Просроченные заказы** (дедлайн прошёл, не CLOSED) | Предупреждение: рост на 10 за день; Критично: общее число > 50 | Прямой индикатор риска жалоб и потери контрактов. | **Warning:** алерт, выгрузка списка для менеджеров/поддержки. **Critical:** тикет с приоритетом, разбор причин (производство, логистика, баг); при необходимости эскалация в саппорт/менеджерам для связи с клиентами; рассмотрение «звонилки» или автоматических напоминаний клиентам. |

### 6.6. Каналы уведомлений (сводка)

- **Чат команды (например, Telegram/Slack):** все предупреждения (Warning) и часть критичных для быстрой реакции.
- **Тикетная система (Jira/YouTrack и т.п.):** все Critical с указанием ответственного (дежурный/команда).
- **Эскалация в саппорт/бизнес:** по согласованному регламенту при критичных бизнес-метриках (массовые просрочки, заполнение хранилища с влиянием на приём заказов).
- **Автоматическая «звонилка» (опционально):** при повторном срабатывании Critical по одному и тому же алерту без закрытия тикета (например, через интеграцию с PagerDuty/Opsgenie или скрипт).

Документ можно дорабатывать после внедрения: уточнять пороги по фактическим графикам и снижать шум алертов.
