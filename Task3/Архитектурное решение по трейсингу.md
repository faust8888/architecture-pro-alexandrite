# Архитектурное решение по трейсингу

Технический документ: внедрение распределённого трейсинга для отслеживания прохождения заказов через систему «Александрит».

---

## 1. Анализ системы и C4-диаграммы в контексте трейсинга

### 1.1. Компоненты, покрываемые трейсингом

Трейсинг должен покрывать весь путь заказа от момента создания до закрытия. По C4-диаграмме и описанию системы в трейсинг включаются:

| Компонент | Роль в потоке заказа | Почему нужен трейсинг |
|-----------|----------------------|------------------------|
| **Shop API** | Приём заказа от клиента, сохранение в Shop DB, загрузка 3D-файла в S3, отправка события в очередь | Начало цепочки B2C; точка, где может «потеряться» заказ при ошибке записи или публикации. |
| **CRM API** | Обработка событий из RabbitMQ, создание/обновление заказа в Shop DB, показ статусов продавцам | Критичное звено B2B: заказ из MES создаётся в CRM только при успешной обработке сообщения. Сбой консьюмера = заказ не появляется в CRM. |
| **MES API** | Расчёт стоимости, назначение на операторов, смена статусов, публикация событий в очередь | Узкое место по времени (2–30 мин расчёт); источник событий для CRM. Задержка или ошибка = заказ «зависает» в ожидании цены. |
| **Messages Queue (RabbitMQ)** | Передача событий о новых заказах и смене статусов между CRM и MES | Сообщения могут застревать, попадать в DLQ или теряться. Трейсинг сообщений (correlation_id) связывает цепочку через очередь. |
| **3d files storage (S3)** | Хранение 3D-моделей для расчёта | Операция загрузки/чтения может завершиться с ошибкой; желательно видеть её в контексте span'а. |
| **Shop DB, MES db** | Хранение заказов и статусов | Запросы к БД — часть цепочки; длительные или неуспешные запросы видны в span'ах. |

Фронтенды (Internet Shop, CRM, MES) — SPA-приложения; трейсинг на бэкенде достаточен для анализа «где застрял заказ». При необходимости можно добавить инструментирование фронтенда (например, для анализа времени отклика UI), но приоритет — бэкенд и очередь.

### 1.2. Места, где заказ может «сломаться» или зависнуть

| № | Место | Сценарий сбоя | Как трейсинг помогает |
|---|-------|----------------|------------------------|
| 1 | **Shop API → Shop DB** | Ошибка записи заказа, таймаут транзакции | Span с ошибкой; видно, на каком запросе упало. |
| 2 | **Shop API → S3** | Ошибка загрузки 3D-файла | Span загрузки; причина отказа (4xx/5xx, timeout). |
| 3 | **Shop API → RabbitMQ** | Сообщение не опубликовано (ошибка подключения, переполнение очереди) | Span публикации; видно, ушло ли сообщение. |
| 4 | **RabbitMQ → CRM API (консьюмер)** | Сообщение в очереди, но консьюмер не обрабатывает (падение, перезапуск) или обрабатывает с ошибкой | Trace показывает: сообщение доставлено (span потребления) или нет; span обработки с ошибкой. |
| 5 | **CRM API → Shop DB** | Ошибка вставки/обновления заказа при обработке события от MES | Span с ошибкой; связь с trace_id/correlation_id сообщения. |
| 6 | **MES API (расчёт стоимости)** | Долгий расчёт (2–30 мин), падение воркера, ошибка доступа к S3 | Span расчёта; видно длительность и этап (чтение файла, расчёт, запись результата). |
| 7 | **MES API → RabbitMQ** | Событие PRICE_CALCULATED не опубликовано | Span публикации; заказ посчитан в MES, но CRM не узнает. |
| 8 | **MES API → MES db** | Ошибка записи статуса или назначения на оператора | Span с ошибкой; видно, на каком запросе заказ «застрял». |
| 9 | **MES API (дашборд)** | Медленный запрос списка заказов | Span запроса; видно, где время (БД, сериализация). |

Трейсинг позволяет по `order_id` или `trace_id` восстановить полный путь заказа и увидеть, на каком участке произошла задержка или ошибка.

### 1.3. Схема: системы, покрытые трейсингом

На диаграмме контейнеров C4 системы, подлежащие инструментированию трейсингом, отмечены и выделены. Новые компоненты (Tracing Backend, Order Flow Monitor) показаны на обновлённых схемах:

## 2. Данные, попадающие в трейсинг

### 2.1. Обязательные данные в span'ах

| Поле | Описание | Зачем нужно |
|------|----------|-------------|
| **trace_id** | Уникальный идентификатор цепочки (trace) | Связь всех span'ов одного бизнес-запроса (например, создание заказа, расчёт цены). |
| **span_id** | Идентификатор отдельного span'а | Иерархия span'ов (parent/child). |
| **parent_span_id** | Идентификатор родительского span'а | Построение дерева вызовов. |
| **service_name** | Имя сервиса (shop_api, crm_api, mes_api) | Фильтрация по компоненту. |
| **operation_name** | Имя операции (например, `order.create`, `price.calculate`) | Понимание, что именно выполнялось. |
| **start_time, duration** | Время начала и длительность | Анализ задержек, поиск узких мест. |
| **status** | ok / error | Быстрый поиск неуспешных операций. |
| **attributes** | Ключ-значение (order_id, correlation_id и т.д.) | Связь с бизнес-сущностями, фильтрация. |

### 2.2. Бизнес-атрибуты (attributes)

| Атрибут | Где задаётся | Назначение |
|---------|--------------|------------|
| **order_id** | Shop API (при создании), CRM API, MES API | Поиск всех span'ов по заказу; связь трейсинга с бизнес-сущностью. |
| **correlation_id** | Сообщения RabbitMQ | Сквозная передача trace_id/correlation_id через очередь; связь span'а консьюмера с span'ом производителя. |
| **message_type** | RabbitMQ (тип события: order.submitted, order.price_calculated и т.д.) | Понимание, какое событие обрабатывается. |
| **source** | MES API | Различение B2C и B2B (ui / b2b_api). |
| **customer_id** | Shop API (опционально, с учётом персональных данных) | Поиск трасс по клиенту; при наличии политики — маскирование или исключение из хранения. |

### 2.3. Передача контекста между компонентами

- **HTTP:** заголовки `traceparent` (W3C Trace Context) или `X-Trace-Id`, `X-Span-Id`.
- **RabbitMQ:** заголовки сообщения `traceparent` или `correlation_id`, `trace_id` — консьюмер извлекает и создаёт дочерний span.
- **Внутренние вызовы:** тот же trace_id передаётся в дочерние span'ы (например, при вызове БД или S3).

## 3. Мотивация

### 3.1. Зачем добавлять трейсинг

- **Быстрая диагностика «застрявших» заказов.** Жалобы «не получил заказ», «работают месяцами» требуют понять: заказ не создан, не попал в очередь, не обработан в CRM, застрял в расчёте MES или в производстве. Без трейсинга — ручной разбор логов по нескольким системам. С трейсингом — один trace по `order_id`, видна вся цепочка и место остановки.
- **Понимание задержек.** Расчёт стоимости 2–30 минут, медленный дашборд MES — трейсинг покажет, сколько времени занимает каждый этап (чтение из S3, расчёт, запись в БД, запрос списка заказов). Это даёт основу для оптимизации.
- **Анализ потери сообщений.** В B2B-сценарии заказ создаётся в CRM по сообщению от MES. Если сообщение потеряно или не обработано, партнёр не видит заказ. Trace по `correlation_id` покажет: сообщение опубликовано, доставлено, обработано или на каком шаге произошла ошибка.
- **Снижение MTTR.** Вместо сбора логов из Shop API, CRM API, MES API и RabbitMQ — один trace. Команда быстрее находит причину инцидента и сокращает время восстановления.

### 3.2. Что это даёт компании

| Результат | Описание |
|-----------|----------|
| Меньше потери контрактов | Быстрая диагностика «потерянных» заказов B2B и прозрачность для партнёров. |
| Сокращение времени разбора инцидентов | Один trace вместо ручного сопоставления логов. |
| Основа для оптимизации | Видны узкие места (расчёт стоимости, запросы к БД). |
| Поддержка SLA | Можно измерять время прохождения заказа по этапам и сравнивать с целевыми значениями. |

### 3.3. Технические и бизнес-метрики, на которые повлияет трейсинг

| Метрика | Как трейсинг влияет |
|---------|---------------------|
| **MTTR (Mean Time To Recovery)** | Сокращение за счёт быстрой локализации сбоя по trace. |
| **Время от SUBMITTED до PRICE_CALCULATED** | Измеряется как сумма длительностей span'ов; можно строить перцентили и алертить при превышении порога. |
| **Доля заказов, «застрявших» в статусе ожидания расчёта** | Трейсинг выявляет причины (ошибка MES, отсутствие сообщения в очереди); можно автоматизировать подсчёт и алертинг. |
| **Количество «потерянных» заказов B2B** | Trace по correlation_id показывает, где оборвалась цепочка; метрика для отчётов и улучшений. |
| **Латентность эндпоинтов MES API** | Span'ы дают разбивку по операциям (БД, расчёт, очередь); точнее, чем только метрики HTTP. |

## 4. Предлагаемое решение

### 4.1. Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| **Протокол/стандарт** | OpenTelemetry | Вендорно-нейтральный стандарт; поддержка Java (Shop API, CRM API) и C# (MES API); возможность смены бэкенда. |
| **Экспорт данных** | OTLP (gRPC или HTTP) | Стандартный протокол OpenTelemetry; поддерживается большинством бэкендов. |
| **Бэкенд трейсинга** | Jaeger или Tempo (Grafana) | Популярные open-source решения; интеграция с Yandex Cloud или self-hosted; UI для просмотра trace. |
| **Хранение** | Совместимое с выбранным бэкендом (например, Elasticsearch для Jaeger, объектное хранилище для Tempo) | Зависит от инфраструктуры; для начала — Managed-сервис или инстанс в облаке. |

### 4.2. Инструментирование компонентов

| Компонент | Действия |
|-----------|----------|
| **Shop API** | Подключить OpenTelemetry Java agent или Spring Cloud Sleuth + Micrometer Tracing; автоматическое создание span'ов для HTTP, JDBC, RabbitMQ; прокидывать `order_id` в attributes при создании заказа. |
| **CRM API** | Аналогично Shop API; при обработке сообщения из RabbitMQ — извлекать `traceparent`/`correlation_id` из заголовков, создавать дочерний span; добавлять `order_id`, `message_type` в attributes. |
| **MES API** | Подключить OpenTelemetry для .NET; инструментировать HTTP, вызовы к БД, S3, публикацию в RabbitMQ; span для расчёта стоимости с `order_id`, `source`. |
| **RabbitMQ** | Передавать `traceparent` в заголовках сообщений; producer и consumer должны читать/писать заголовки. Бэкенд RabbitMQ в trace не инструментируется отдельно — он виден как «пропуск» между span'ами producer и consumer. |

### 4.3. Новые компоненты на архитектуре

- **Tracing Backend** — сервис приёма, хранения и отображения трейсов (Jaeger/Tempo). Размещается в облаке (Yandex Cloud) или на отдельном инстансе. Подключения: Shop API, CRM API, MES API отправляют трейсы по OTLP.

Схема с новыми компонентами (выделены красным): [resource/jewerly_c4_tracing.drawio](resource/jewerly_c4_tracing.drawio)

### 4.4. Автоматический мониторинг процесса прохождения заказа и алертинг

На основе данных трейсинга можно реализовать автоматический мониторинг и алертинг:

- **Агрегация метрик из трейсов.** Периодически (например, каждые 5–15 минут) выбирать из бэкенда трейсов trace'ы с `order_id` и атрибутами `order.submitted`, `order.price_calculated` и т.д. Вычислять:
  - время от начала trace до span'а `price.calculate` (completed);
  - количество trace'ов, где span `price.calculate` в статусе error или отсутствует при наличии `order.submitted` (заказ «застрял» в расчёте).
- **Экспорт в систему метрик.** Prometheus или аналог — экспортер или скрипт, который запрашивает агрегированные данные из Jaeger/Tempo API и выставляет gauge/counter в Prometheus.
- **Алерты.** Правила в Prometheus/Alertmanager: например, «заказов в ожидании расчёта > 15 мин — больше 20» или «доля ошибок в span'ах обработки сообщений CRM > 5%».
- **Order Flow Monitor (опциональный сервис).** Отдельный компонент, который подписывается на события из трейс-бэкенда (если поддерживается) или периодически опрашивает API, агрегирует метрики и отправляет их в Prometheus. При превышении порогов — создаёт тикет или отправляет алерт в чат.

Схема с компонентом мониторинга (выделен зелёным): [resource/jewerly_c4_tracing_monitoring.drawio](resource/jewerly_c4_tracing_monitoring.drawio)

## 5. Компромиссы

### 5.1. Когда трейсинг не принесёт пользы

- **Разовые, несвязанные ошибки.** Если сбой случается редко и не воспроизводится, trace может уже быть удалён (по политике хранения). Трейсинг помогает при повторяющихся или массовых инцидентах.
- **Проблемы вне инструментированного пути.** Сбои на уровне сети, инфраструктуры (EC2, БД), которые не отражаются в span'ах приложений, трейсинг не покажет. Нужен мониторинг инфраструктуры отдельно.
- **Человеческий фактор.** Задержки из-за того, что оператор не взял заказ в работу, трейсинг не объяснит — это бизнес-процесс, а не технический.

### 5.2. Когда реализация пока невозможна или слишком дорога

- **MES — проприетарный софт с закрытым кодом.** Если MES API нельзя модифицировать (нет доступа к коду или вендор не поддерживает), инструментировать его изнутри не получится. Возможные обходы: sidecar-прокси с трейсингом перед MES API или логирование на границе (nginx/API gateway) — но полнота trace будет ограничена.
- **Ограничения по ресурсам.** Хранение трейсов и объём трафика (sampling) влияют на стоимость. При высокой нагрузке потребуется sampling (например, 10% успешных, 100% с ошибками); часть трасс будет недоступна для разбора.
- **Разные команды и стек.** Shop/CRM на Java, MES на C# — требуют отдельных настроек OpenTelemetry. Команда должна обладать экспертизой в обоих стеках или привлечь консультантов.
- **RabbitMQ без поддержки заголовков в старых клиентах.** Если используется старая версия клиента, не передающая заголовки, сквозной trace через очередь будет разорван. Нужна модернизация клиентов.

### 5.3. Альтернативы при ограничениях

- **Только логирование correlation_id.** Минимальный вариант: прокидывать `order_id`/`correlation_id` в логах и сообщениях; искать по `order_id` в логах всех сервисов. Дешевле, но ручнее, чем полноценный трейсинг.
- **Event sourcing / audit log заказов.** Отдельная таблица или лог событий по заказу (создан, отправлен в очередь, обработан, цена посчитана и т.д.). Даёт бизнес-историю, но не технические детали (латентность, ошибки на уровне HTTP/БД).

## 6. Безопасность

### 6.1. Внутри компании

- **Доступ к UI трейс-бэкенда.** Только сотрудники с ролью «Поддержка», «Разработчик», «DevOps» или «Администратор». Аутентификация через корпоративный IdP (например, OAuth/SSO).
- **Данные в span'ах.** Не хранить персональные данные (ФИО, email, телефон) в attributes. `order_id`, `correlation_id`, `message_type` — допустимы. При необходимости `customer_id` — маскировать или не выводить в UI по умолчанию.
- **Сеть.** Tracing Backend доступен только из внутренней сети/VPC. Приложения отправляют трейсы по внутреннему адресу.
- **Хранение.** Политика хранения трейсов (например, 7–14 дней в prod) для ограничения объёма и рисков утечки.

### 6.2. Снаружи (если потребуется)

- **Партнёры B2B.** Трейсинг — внутренний инструмент. Партнёрам не даётся доступ к UI трейсов. При необходимости поддержка может по запросу партнёра (по `order_id`) найти trace и сообщить статус без раскрытия внутренней архитектуры.
- **SaaS-бэкенд трейсинга.** Если используется облачный бэкенд (не self-hosted), трафик трейсов должен идти по шифрованному каналу (TLS). Проверить, что провайдер соответствует требованиям по хранению данных (например, резиденство данных).

### 6.3. Рекомендации

- Внедрить аутентификацию и авторизацию для UI трейс-бэкенда с первого дня.
- Документировать политику хранения и правила работы с персональными данными в трейсах.
- Регулярно аудировать, кто имеет доступ к трейс-бэкенду.
